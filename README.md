# 赔款发展三角 · 月结网页

精算月结工具：Flask + SQLite。按月导入赔款 CSV（支持同一赔款号分多笔付款、
承接历史无流水旧笔）、逐月封账、按（事故月 × 支付月）净变动归档汇总，
并可按任一已结月回查当时的累计赔付发展三角。

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据保存在名为 `closing-data` 的卷中（容器内 `/data/closing.db`）。
删除数据重来：`docker compose down -v`。

## 付款模型（重要）

导入的每一行是一笔**付款**，由「赔款号 + 付款流水号」共同定位：

| 概念 | 说明 |
| --- | --- |
| 无流水旧笔 | `payment_ref` 留空的付款；同一赔款号至多一笔。历史版本导入的数据全部属于此类。 |
| 流水付款 | 填了 `payment_ref` 的付款；同一赔款号可有多笔流水，各自独立入账。 |
| 同流水重报 | 只覆盖该流水这一笔（可改事故月、支付月、金额），不触碰同号其他流水。 |
| 承接旧笔 | 旧笔第一次带上流水号时，用 `assume_legacy=1` 指定该流水承接它。承接后复用同一条付款记录（同一个归档快照），所以只补流水号不产生净额；之后该赔款号的无流水重报仍更正这笔。 |
| 承接约束 | 只有已有无流水旧笔才能标记承接；首次报送流水时必须在本批用**恰好一条**行来承接；承接关系一经建立不能改绑。 |
| 无旧笔的赔款号 | 一旦报送过流水，就拒收该赔款号的无流水行（同批或跨批都一样）。 |
| 同笔冲突 | 同一批内两行若最终指向同一笔付款（同流水、或一条承接旧笔而另一条无流水等），整批退回，判定与行序无关。 |

承接与整批入账在同一个 SQLite 事务里提交；任何校验冲突、承接冲突或写入失败
都会整批回滚，不留部分结果。

## 网页演示流程（分期 + 承接 + 两期回查）

仓库自带四批演示数据：

- `demo/claims_2026-01_base.csv`：基础批，7 笔，全部是无流水旧笔；
- `demo/claims_2026-02_supplement.csv`：补报 + 更正批；
- `demo/claims_2026-03_installments.csv`：同一赔款号分期 + 承接旧笔；
- `demo/claims_2026-03_conflict.csv`：两行指向同一笔付款的冲突样本（应整批退回）。

1. **设置首个待结月**：首页 →「待结月设置」→ 填 `2026-01`。
2. **导入基础批**：「导入赔款」→ 选择 `claims_2026-01_base.csv` → 导入
   （7 笔，计入 2026-01 期）。
3. **封账 2026-01**：「封账」页可预览本期净变动组合 → 确认封账，待结月推进到 2026-02。
4. **导入补报/更正批**：导入 `claims_2026-02_supplement.csv`（7 笔，其中 3 笔同号覆盖：
   C-0002 改金额 80000→95000；C-0004 改支付月 2026-01→2026-02；C-0007 同数重报）。
5. **封账 2026-02**：本期只归档 6 个净变动组合（C-0007 无净变动，不产生归档行）。
6. **导入分期/承接批**：导入 `claims_2026-03_installments.csv`：
   - C-0005 用 `PAY-0001`（承接旧笔，金额/月份不变，故无净额）留在 2025-12，
     另有 `PAY-0002` 25,000 计入 2026-03；
   - C-0007 用 `PAY-0003` 承接旧笔，无净额；
   - C-0012 是从未有过旧笔的新赔款号，两笔流水 `PAY-0004` / `PAY-0005` 分别入账。
7. **导入冲突样本**：导入 `claims_2026-03_conflict.csv`，页面应提示两行指向同一笔付款、
   整批退回，库中数据不变。
8. **封账 2026-03**：本期归档 3 个净变动组合，待结月推进到 2026-04。
9. **三期回查**：「三角回查」起始事故月选 `2025-10`：
   - 已结月选 `2026-01`：仍是当时口径（如 2025-10 事故月 2025-12 累计 200,000），
     2026-02 列留空（封账月之后留空）；
   - 已结月选 `2026-03`：含补报、更正与分期付款；
   - 「归档明细」可查看每期净变动组合（只读汇总）。

也可以脚本化演示（服务已启动时）：

```bash
bash scripts/demo_curl.sh http://127.0.0.1:8000
```

## CSV 格式

必需四列，另有可选两列（顺序不限，支持中英文别名）：

```csv
claim_no,accident_month,payment_month,amount_cents,payment_ref,assume_legacy
C-0001,2025-10,2025-10,120000,,
C-0005,2025-12,2025-12,200000,PAY-0001,1
C-0005,2025-12,2026-03,25000,PAY-0002,0
```

- `claim_no`：赔款号。
- `accident_month` / `payment_month`：`YYYY-MM`；支付月须在事故月至当前待结月之间（含首尾）。
- `amount_cents`：非负整数，单位分。
- `payment_ref`（可选，别名「付款流水号」）：付款流水号。留空表示无流水旧笔；
  同一赔款号下无流水行至多一笔。
- `assume_legacy`（可选，别名「承接旧笔」）：填 `1` 表示该流水承接该赔款号已有的
  无流水旧笔；只能用于已有旧笔，且必须填流水号。留空或 `0` 表示普通入账。
- 任一行非法或冲突 → 整批拒绝，不留部分结果。

## 已有数据库直接升级

启动时会自动把旧版 `claims` / `claim_archived` 表迁移为 `payments` /
`payment_archived`：每笔旧赔案变成一条无流水旧笔，归档快照按同一赔款号挂到新的
付款记录上，`meta` / `batches` / `closes` / `archive` 原样保留。迁移后可继续导入、
封账，旧库的已结三角仍按原数回查。迁移是单事务的，失败会回滚并保持旧表可用。

## 本地开发与自测

```bash
pip install -r requirements.txt
python run.py                 # http://127.0.0.1:8000 ，数据在 ./data/closing.db
python tests/selftest.py      # 关键操作自测（不依赖 pytest）
```

自测覆盖：CSV 校验、同流水覆盖与多流水分笔、承接（首次承接 / 只补流水号无净额 /
承接后无流水重报仍更正 / 不可改绑 / 只能承接旧笔）、无旧笔拒收无流水、
同批混填与同笔冲突（行序无关）、整批原子性、旧库迁移、两期回查、并发导入与封账。

## 设计要点

- **期间归属**：每批记录导入时的待结月为所属期间；封账时只归档本期批次的净变动。
  导入与封账重叠时，进程内写锁 + SQLite `BEGIN IMMEDIATE` 单事务保证整批按提交
  先后计入本期或下期，失败整体回滚。
- **增量归档**：`payment_archived` 以 `payment_id` 为键保存每笔付款最近封账时的快照；
  封账时对本期触及的付款做「当前值 − 归档快照」差分，只为净变动非零的
  （事故月 × 支付月）组合写 `archive` 行，随后推进快照与待结月。承接旧笔复用同一
  `payment_id`，快照仍指向旧笔上次封账的金额与月份，因此只补流水号不产生净额。
- **只读回查**：三角回查只读 `archive` 汇总（`close_month ≤ 所选已结月` 求和后逐月
  累计），已结三角不受后续补报/更正影响。列范围到最新已结月，封账月之后留空，
  事故月之前显示「—」，已到月份零额显示 0。
- **封账约束**：只能封当前待结月，成功后自动进入次月；有数据后首个待结月不可再改。

## 已知限制

- 使用 Flask 内置服务器（单进程多线程），面向内部演示/小团队；生产化可换
  gunicorn（须保持单 worker 以维持进程内写锁，或改用数据库级互斥）。
- 无登录鉴权；金额上限 15 位整数分；时间戳为 UTC。
- 旧笔若在迁移前从未封账（没有归档快照），首次承接时其金额会全额计入当期净变动；
  「沿用上次封账金额」只适用于已有快照的旧笔。
